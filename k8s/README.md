# WikiGuard's cluster

> **Not deployed.** The chart runs on kind on a laptop (`scripts/kind_cluster.py`). The VM steps below were written for Oracle Cloud's free ARM VM, which never had capacity, and have never run on one. The public demo runs without a cluster: the API on Render serves a scored snapshot of real edits.

Everything that runs in Kubernetes: the stream, the scheduled jobs, retraining, monitoring, and how
the cluster is built and kept in step with this repo. The API runs on Render and the frontend on
Vercel; neither is here.

```
k8s/
  charts/wikiguard/      the app: Redpanda, ingestor, scorer, archiver, the CronJobs, the trainer
                         Job template, NetworkPolicies, RBAC, alerts, and the Grafana dashboards
    values.yaml          production (k3s on the Oracle VM)
    values-kind.yaml     what differs on the laptop
    images.yaml          each image's digest, written by CD's pull request (DEC-084)
    dashboards/          generated by scripts/build_dashboards.py, never edited by hand
  platform/              namespaces with their Pod Security levels, and values for
                         kube-prometheus-stack and Argo CD
  argocd/                the root Application and the apps it syncs from GitHub
  kind/                  the laptop's cluster config and its stand-ins
  secrets/prod/          SealedSecrets, safe to commit: only the cluster can open them
```

## On the laptop (kind)

Needs Docker Desktop, kind, kubectl, and Helm. Nothing needs an account.

```bash
python scripts/kind_cluster.py up        # cluster, images, monitoring, secrets, chart (about an hour the first time)
python scripts/kind_cluster.py images scorer   # rebuild one image and load it
python scripts/kind_cluster.py install   # helm upgrade after a chart change
python scripts/kind_cluster.py down      # delete it all
```

Postgres runs in the cluster in place of Supabase, the archive and backups stay on volumes, the
models come from DagsHub's public MLflow, and `alert-sink` in `monitoring` stands in for Discord and
Healthchecks.io. The ingestor reads the live Wikimedia stream. Grafana:

```bash
kubectl --context kind-wikiguard -n monitoring port-forward svc/kps-grafana 3000:80
# user admin, password in data/kind/grafana_password.txt
```

## On the Oracle VM

1. `sudo bash scripts/harden_vm.sh`, then `sudo tailscale up --ssh`. Once `tailscale ssh` works,
   delete the security list's ingress rule for port 22 in the Oracle console. The VM then takes no
   traffic from the internet at all.
2. `sudo bash scripts/bootstrap_cluster.sh`. It installs k3s and Argo CD, and Argo CD pulls
   everything else from `main`.
3. Back up the Sealed Secrets key to the password manager, straight away:
   `kubectl -n sealed-secrets get secret -l sealedsecrets.bitnami.com/sealed-secrets-key -o yaml`.
   A rebuilt cluster needs it (`--sealed-secrets-key`), or every sealed file must be sealed again.
4. Seal each Secret below with `scripts/seal_secrets.sh`, commit the files in `k8s/secrets/prod/`,
   and push. Argo CD applies them.
5. Set the bucket and the backup's public key in `values.yaml` (`ARCHIVE_S3_*`, `BACKUP_PUBLIC_KEY`).
6. Set the repository variable `CLUSTER_ENABLED` to `true`, so CD proposes image digests.

Rebuilding after Oracle reclaims the VM is the same, with `--sealed-secrets-key FILE
--restore-archive`. The runbook is `docs/runbooks/cluster-rebuild.md`.

## Secrets

Each component reads only its own Secret, named `wikiguard-COMPONENT` in the `wikiguard` namespace.
A leaked one gives away only that component's access (section 8 of the plan).

| Secret | Keys |
|---|---|
| `wikiguard-ingestor` | `USER_HASH_KEY`, `SENTRY_DSN` (optional) |
| `wikiguard-scorer` | `DATABASE_URL` (as `scorer_login`), `SENTRY_DSN` (optional) |
| `wikiguard-archiver` | `ARCHIVE_S3_ACCESS_KEY`, `ARCHIVE_S3_SECRET_KEY`, `SENTRY_DSN` (optional) |
| `wikiguard-labeler` | `DATABASE_URL` (as `labeler_login`) |
| `wikiguard-monitor` | `DATABASE_URL` (as `trainer_login`), `DISCORD_WEBHOOK_URL`, `HEALTHCHECKS_PING_URL` |
| `wikiguard-purge` | `DATABASE_URL` (as `maintenance_login`), `USER_HASH_KEY` |
| `wikiguard-purge-snapshots` | `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` (DagsHub's DVC token, both), `DISCORD_WEBHOOK_URL` |
| `wikiguard-retention` | `DATABASE_URL` (as `maintenance_login`), `DISCORD_WEBHOOK_URL` |
| `wikiguard-backup` | `DATABASE_URL` (as `backup_login`), `ARCHIVE_S3_ACCESS_KEY`, `ARCHIVE_S3_SECRET_KEY` |
| `wikiguard-retrain-poller` | `DATABASE_URL` (as `trainer_login`) |

In `monitoring`:

| Secret | Keys |
|---|---|
| `wikiguard-alerting` | `discord-webhook-url`, `healthchecks-url` (Alertmanager reads them as files) |
| `grafana-admin` | `admin-user`, `admin-password` |

Database URLs use Supabase's transaction pooler, as `README.md` describes, each with its own login.

## What keeps it safe

- **Pod Security `restricted`** on the `wikiguard` namespace: every pod non-root, no privilege
  escalation, every capability dropped, seccomp on, a read-only root filesystem, and limits.
  `tests/test_k8s_chart.py` renders the chart and checks every pod, including the trainer Job.
- **Default-deny networking**, in and out. Each component's `egress` list in `values.yaml` opens
  only the paths it needs. Only the ingestor, scorer, archiver, and labeler reach Redpanda.
- **One API token in the namespace**: the retrain poller's, which may create, read, and delete Jobs
  there and nothing else.
- **Nothing exposed**: no Ingress, LoadBalancer, or NodePort. The admin path is Tailscale.
- **kubescape** (NSA and MITRE frameworks): see `docs/security.md` for the last run and the
  findings left open.
